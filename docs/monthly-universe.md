# Monthly stock universe

The data worker registers BullMQ scheduler `monthly-stock-universe` in the persistent `quantforge-jobs` queue with cron `0 0 2 1 * *`, timezone `Asia/Kolkata`. This means the **1st at 02:00 IST**, not 02:00 UTC. A single active scheduler ID is upserted on worker startup.

At startup, the worker also checks whether a successful instrument-master import exists after the current cycle's due time. If missing, one deduplicated catch-up job is queued. Before 02:00 on the 1st, the preceding month's cycle is current. A successful manual refresh counts as satisfying the cycle. Failed refreshes retry five times with exponential backoff starting at one minute. Exhausted failures appear in Connections & Data; a manual instrument-master import can retry, and restarting the worker retries a failed catch-up job.

The master comes from Dhan's public instrument CSV and does not require a daily Dhan access token. Only NSE/BSE cash-equity company listings are imported. Bonds, funds and derivatives are excluded. One primary listing per ISIN is used when qualification scans the company universe.

Before publication, the importer rejects duplicate IDs, unexpected changes of company identity, missing exchange coverage, implausibly small snapshots and drops of more than 20% in either exchange's active listing count. The existing universe is retained on failure. All updates publish in a MongoDB transaction. Missing listings become inactive rather than being deleted. Broker mappings on retained listings and all historical data remain intact. New company and listing counts are stored with the source run.

This schedule updates the **instrument universe only**. It does not add new listings directly to the qualified list, rerun saved rules, auto-publish a scan, import company metrics or backfill price history. Those operations have their own explicit controls. Newly listed stocks may lack enough completed months for an EMA rule and are reported as unavailable where necessary.

Connections & Data shows the next scheduled time, last successful refresh, new additions and worker heartbeat. The heartbeat expires after 35 seconds. On DigitalOcean, run the existing data-worker process continuously alongside persistent MongoDB and Redis. No desktop schedule can execute while the workstation is off; startup catch-up handles that case when services return.

Qualification's coverage panel counts available observations for the saved rule across active primary listings, refreshed at most every 15 seconds. Both operands and crossover lookbacks are included. Technical coverage requires enough consecutive monthly observations ending in the most recently completed month. Newly listed stocks cannot be assigned invented history. Per-session completeness still depends on the provider's daily history. The engine rejects stale monthly prices and restarts indicator warm-up after missing months.

Run saved rules and Save and run queue preparation and evaluation together. The worker checks existing inputs, loads missing supported company metrics for stocks that could still qualify, checks the rules again, then downloads the necessary daily history. Only a definitive rejection from the engine's AND/OR logic can skip a download; an unknown condition cannot. The calculation snapshot cutoff is fixed after preparation, so newly collected facts are visible to the scan. Preparation never publishes a list or changes saved rules.

For EMA 5 / EMA 21, 63 months of daily history provide additional warm-up while excluding the forming month. Completed ranges are recorded in dataset_receipts; repeats reuse them. Company snapshots are shared by ISIN across both listings, retain their collection timestamps, and omitted metrics remain unknown. A successful company query that omits a field is cached for one day to avoid repeating unavailable data requests. Current snapshots must not be backdated into historical backtests.

Dhan requests share a Redis limiter across processes. Historical requests are spaced at 260 ms (below the documented five-per-second maximum); company requests use a conservative 1.5-second spacing after observed throttling. HTTP 429 honours Retry-After where supplied, otherwise pauses for one minute, with bounded retries and a shared cooldown shown in the UI. A failed/cancelled run retains cached data; a subsequent run reuses it. First full import duration depends on the provider and the saved rule. Publication remains an explicit review step.

The monthly AI assistant calls Gemini through the backend and validates the proposed conditions against the supported monthly rule contract. It can ask for clarification when a request cannot be represented. Applying a proposal marks the manual form dirty; Save rule and Save and run remain explicit user actions.
